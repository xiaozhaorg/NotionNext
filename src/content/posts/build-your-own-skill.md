你有没有遇到过这种事：同一件事教了 AI 八遍，下次开个新对话，它又全忘了。或者每次都得把一大段提示词复制来复制去，烦都烦死了。

Skill 就是来解决这个的。这篇我不跟你讲玄的，就用一个例子从头做到尾——**做一个"自动生成 git 提交信息"的 Skill**：从它是什么，一路写到怎么测、怎么打包给别人用。看完你就能照着做出自己的第一个 Skill。

如果你已经看过我那篇[把 Agent Skills 字段讲清楚](./agent-skills/)的文章，那篇管"字段怎么写才对"，这篇管"从零动手做"，两篇正好配着看。

## 一、Skill 到底是什么

一句话：**Skill 是一个文件夹，里面装着"教 AI 怎么干某件事"的说明书，AI 需要的时候才会翻开它。**

打个比方。你把 AI 想象成一个新来的实习生：

- **提示词（prompt）**＝你当面口头交代的一句话。说完就完，下次得重说。
- **Skill**＝你给他写的一本岗位手册，放在书架（Skill 目录）上。书脊上印着书名和一句话简介（`name` 和 `description`）。他路过书架扫一眼简介，觉得"这活儿跟我现在干的有关"，才把整本书抽出来看。
- **MCP**＝给他接的工具和接口，比如公司的 Git 系统、数据库。手册（Skill）教他**怎么用**这些工具完成一项复杂工作，两者是配合关系，不是替代。

关键就在"扫一眼简介才翻书"这个动作。AI 启动时，**只读所有 Skill 的书名和简介**，不读正文。等任务真的对上了，才把整本手册加载进来。这个做法叫**渐进式披露**——说白了就是按需翻书——所以你可以装几十上百个 Skill，平时几乎不占脑子（上下文）。

一个 Skill 的目录长这样：

```
commit-message-writer/        ← 文件夹名 = Skill 名
├── SKILL.md                  ← 必须：说明书本体（元数据 + 正文）
├── scripts/                  ← 可选：能直接跑的代码
├── references/               ← 可选：需要时才查的详细文档
└── assets/                   ← 可选：模板、图片等素材
```

**什么时候值得做成 Skill？** 一个很实用的判断标准：**同一件事你重复做了五次以上**，而且每次步骤、格式、规矩都差不多——固定格式的周报、某类 bug 的排查流程、团队的代码审查清单——那就该写成 Skill。一次性、天马行空的事（比如"写首关于夏天的诗"）没必要。

## 二、动手前，先把几条规矩说清楚

在动手写之前，把几条硬规矩记住，能帮你避开新手 90% 的坑。

### 1. 目录名就是 Skill 名

文件夹叫什么，`SKILL.md` 里的 `name` 就必须叫什么。规则是：**1–64 字符，只能用小写字母、数字和连字符，不能以连字符开头或结尾，不能有连续连字符**。

所以 `Commit Message Writer`、`-commit`、`commit--writer` 全是错的，`commit-message-writer` 才对。

### 2. 开头那段信息，必填两项，其余看情况

`SKILL.md` 开头有一段 YAML 信息（正式叫 frontmatter），用 `---` 包起来。必填的只有两个字段：

```yaml
---
name: commit-message-writer
description: 根据 git 改动生成符合 Conventional Commits 规范的提交信息。当用户需要写 commit message、提交代码、描述本次改动，或提到 git commit 时使用。
---
```

- `name`：上面说过了。
- `description`：**这是最关键的一个字段**，后面会单独讲——它决定了 AI 会不会用你的 Skill。

可选的还有：`license`（许可证）、`compatibility`（环境要求，比如"需要 Python 3.14 和 uv"）、`metadata`（自定义键值）、`allowed-tools`（预先批准的工具，实验性，支持度不一）。**大多数 Skill 用不到这些，别画蛇添足。**

### 3. description 是"触发开关"，不是"功能介绍"

新手最容易犯的错，就是把 description 写成一句干巴巴的功能介绍，比如 `description: 生成提交信息`。结果 AI 根本想不起来用它。

正确的写法要同时回答三个问题：**它做什么 + 什么时候用 + 用户会怎么说**。而且官方也提到，AI 有个毛病：明明该用这个 Skill，它却想不起来用。所以 description 要写得稍微"黏人"一点，把各种说法都列上：

```yaml
description: 根据 git 改动生成符合 Conventional Commits 规范的提交信息。当用户需要写 commit message、提交代码、描述本次改动，或提到 git commit 时使用。即使用户没有明说"规范格式"，只要他说"帮我提交""写个提交说明"，也要用这个 Skill。
```

这里还有个小提醒：**特别简单的一步任务，比如"读一下这个文件"，AI 往往不会去用 Skill**，因为它自己直接就能干。这不代表你的 Skill 坏了——复杂、多步骤的任务才会稳定触发。测的时候要选有分量的任务。

### 4. 正文怎么写：讲清"为什么"，别堆"必须"

开头那段信息下面是 Markdown 正文，写具体的操作说明。几条好用的写法：

- **用祈使句**："运行 git diff"、"判断改动类型"，而不是"你应该运行……"。
- **解释原因，而不是堆 MUST**：现在的 AI 很聪明，你告诉它"为什么这么做"，比写十个加粗的"必须"更有效。满屏 `ALWAYS`/`NEVER` 是危险信号。
- **给输入输出的例子**：一条好例子胜过三段描述。
- **把输出格式写成模板**：需要固定格式时，直接给一个照抄的模板。

### 5. 三层加载，别把书写厚了

前面说的分三层加载，记一下大致的"体重"：

| 层级 | 内容 | 什么时候加载 | 预算 |
| --- | --- | --- | --- |
| 第一级 | `name` + `description` | 启动时常驻 | 约 100 tokens |
| 第二级 | `SKILL.md` 正文 | 命中时整篇读入 | 建议 < 5000 tokens |
| 第三级 | `scripts/`、`references/`、`assets/` | 需要时才读/跑 | 按需，几乎不限 |

所以有个硬建议：**`SKILL.md` 正文控制在 500 行以内**。超了就把详细内容拆到 `references/` 里，在正文里指个路："具体规范见 [references/conventions.md](references/conventions.md)"。而且引用路径要从 Skill 根目录写相对路径，**只引用一层，别套娃**。

对于大文件（超过 300 行），加个目录。对于多框架、多领域的情况，按变体分文件——比如云部署的 Skill 拆成 `references/aws.md`、`gcp.md`、`azure.md`，AI 只读相关的那一个。

## 三、完整实例：从零做出 commit-message-writer

规矩讲完，开始真刀真枪做。跟着走一遍你就懂了。

### 第 1 步：先想清楚（别急着写）

动手前先回答四个问题，这是官方 skill-creator 的第一步，先把要干嘛想清楚：

1. **这个 Skill 要让 AI 做什么？** —— 根据 git 改动生成提交信息。
2. **什么时候触发？** —— 用户说"帮我提交""写个 commit""描述这次改动"的时候。
3. **输出长什么样？** —— 一段符合 Conventional Commits 格式的文本。
4. **要不要测试？** —— 要。因为输出格式是可客观检验的（前缀对不对、有没有超 50 字），这类 Skill 最适合测试。

同时把边界情况想清楚：用户没暂存代码怎么办？一次提交混了好几件不相关的事怎么办？这些都会写进正文。

### 第 2 步：建目录，写 SKILL.md

建一个 `commit-message-writer/` 文件夹，里面放 `SKILL.md`。这是完整内容：

```markdown
---
name: commit-message-writer
description: 根据 git 改动生成符合 Conventional Commits 规范的提交信息。当用户需要写 commit message、提交代码、描述本次改动，或提到 git commit 时使用。即使用户没有明说"规范格式"，只要他说"帮我提交""写个提交说明"，也要用这个 Skill。
---

# 提交信息生成器

根据当前 git 改动，生成一条清晰、符合规范的提交信息。

## 步骤

1. 先运行 `git diff --staged` 看暂存区改动。若暂存区为空，运行 `git diff` 并提醒用户先 `git add`。
2. 判断改动类型，选前缀：
   - `feat`：新功能
   - `fix`：修复 bug
   - `docs`：只改文档
   - `refactor`：重构，不改变外部行为
   - `chore`：构建、依赖、杂项
3. 写标题：`<type>(<scope>): <简短描述>`，不超过 50 字符，动词开头，结尾不加句号。
4. 需要正文时，空一行后写"为什么"这么改，不要重复"改了什么"。
5. 团队特殊约定见 [references/conventions.md](references/conventions.md)。

## 输出格式

只输出提交信息本身，用代码块包裹，不要额外解释：

    feat(auth): add JWT token refresh

    Refresh tokens 30 minutes before expiry so users aren't logged out mid-form.

## 常见情况

- 一次混了多个不相关改动：建议用户拆成多次提交，不要硬塞进一条。
- 纯格式化改动：用 `style`，别伪装成 `refactor`。
```

注意几个细节：正文是祈使句；给了完整的输入输出例子；输出格式写成了照抄模板；每个规则后面都隐含了"为什么"（比如"不超过 50 字符"是为了在 git log 里好看）。

### 第 3 步：按需加 references 和 scripts

团队的提交规范可能因项目而异，塞进正文会让 `SKILL.md` 变臃肿。拆到 `references/conventions.md`：

```markdown
# 团队提交约定

- scope 用模块名，如 `auth`、`api`、`ui`；跨模块用 `core`。
- 破坏性改动在类型后加 `!`，如 `feat(api)!: drop v1 endpoint`，并在正文写迁移说明。
- 关联工单在正文末尾单独一行：`Refs: #1234`。
```

如果有个步骤是**固定、重复的活**——比如格式化输出、解析 diff——那就写成 `scripts/` 里的脚本让 AI 直接跑，而不是让它一个字一个字生成。官方也强调过：跑代码比让模型生成同样的文本更便宜、更可靠。**这类脚本要自己能跑、报错说人话、遇到特殊情况也不崩。**

到这里，你的文件夹就是：

```
commit-message-writer/
├── SKILL.md
└── references/
    └── conventions.md
```

这样，一个能用的 Skill 就有了。但**别急着发出去——先测。**

## 四、测试流程：怎么知道它到底好不好用

这是最多人跳过、也最不该跳过的一步。测试要回答两个问题：**该触发时触发了吗？**（触发准不准）以及**触发后干得好不好？**（效果行不行）。

### 第 1 步：写几条真实测试用例

想 2–3 个真实用户会说的话——不是"格式化数据"这种抽象指令，而是有细节的具体场景。存成 `evals/evals.json`：

```json
{
  "skill_name": "commit-message-writer",
  "evals": [
    {
      "id": 1,
      "prompt": "我刚给登录模块加了 JWT 刷新，改动都暂存了，帮我写个提交信息",
      "expected_output": "一条 feat(auth) 开头、50 字符内的提交信息",
      "files": []
    },
    {
      "id": 2,
      "prompt": "这次改动其实是我手滑格式化了半个项目，帮我提交下",
      "expected_output": "识别出这是纯格式化改动，用 style 前缀",
      "files": []
    }
  ]
}
```

先**只写提示词，别写断言。断言是下一步的事。**

### 第 2 步：同一批任务，跑两遍对照

关键动作：**每个测试用例都跑两次**——一次带着你的 Skill，一次不带（叫 baseline 对照组）。**两批要同时开跑**，别先跑完一批再跑另一批。

为什么要对照？因为如果"不带 Skill"也能做得一样好，说明你这个 Skill 没价值。只有带 Skill 明显更好，才算过关。

（如果你是在改进一个已有的 Skill，对照组应该用**旧版本**——改之前先复制一份快照。）

在 Claude Code 里，官方 skill-creator 会自动帮你起这些测试任务；在 Claude.ai 这种没有子代理帮忙的环境，就手动一条条跑：读一遍 `SKILL.md`，照着它完成测试任务，把结果存到工作区。

### 第 3 步：边跑边写断言

任务在后台跑的时候别闲着，给每条测试写**可客观检验的断言**。比如：

- 提交信息是否以 `feat(` 或 `fix(` 等合法前缀开头
- 标题是否 ≤ 50 字符
- 是否用了代码块包裹、没有多余解释

断言要能机器判定、名字要一看就懂。主观的东西（文风好不好）别硬写断言，留给人来看。

### 第 4 步：打分、汇总、让人看结果

跑完后：

1. **逐条打分**：每条断言标记通过/失败，并附上证据。能量化的就写脚本自动检查，比肉眼快也可靠。
2. **汇总成 benchmark**：用聚合脚本生成 `benchmark.json`，对比"带 Skill"和"不带"的通过率、耗时、token 消耗。
3. **生成 review 页面**：官方用 `generate_review.py` 生成一个网页，左边逐个看输出、写反馈，右边看量化对比。迭代第二轮以后，还能看到和上一轮的对比。
4. **读反馈、改 Skill、再跑下一轮**：存成 `iteration-2/`、`iteration-3/`。重复到满意为止。

这里有个官方反复强调的做法：**改进要从具体反馈里找共性，而不是为某一条测试打补丁**。Skill 是要用成千上万次的，如果只对你这几条测试有效，那就废了。发现所有测试里 AI 都自己写了类似的辅助脚本？那就把它固化进 `scripts/`。发现某段指令让 AI 绕路？删掉它。

### 第 5 步：专项优化"触发准不准"

效果调好了，还有一件专门的事：**优化 description 的触发准确率**。

做法是造 **20 个查询**，一半"该触发"、一半"不该触发"（官方建议各 8–10 个）。诀窍在于：**不该触发的要选"擦边球"**——跟你的 Skill 共享关键词、但其实需要别的处理。比如给提交信息 Skill 造反例："帮我看看这个 git log 里谁改得最多"——提到 git，但不需要写提交信息。太离谱的反例（"写个斐波那契函数"）测不出东西。

然后把这批查询按 **60% 拿来调 / 40% 留着考**分开，每条跑 3 次看触发率，让 AI 根据失败的案例改写 description，最多改 5 轮，最后**用留着的那部分打分，选成绩最好的那版**（免得只背下这几道题的答案，换个问法就不会了）。这一步在 Claude Code 里用 `run_loop` 脚本自动跑。

### 什么时候可以跳过测试

如果你的 Skill 产出是**主观的**——写作风格、设计审美——客观断言意义不大，靠人看反馈就够了。但凡输出可验证（文件转换、数据抽取、代码生成、固定流程），测试都值得做。

## 五、校验、打包、安装

写完之后收个尾：

**校验格式。** 用官方的 `skills-ref` 库检查开头那段信息是否合法、命名是否合规：

```bash
skills-ref validate ./commit-message-writer
```

**打包。** 用 skill-creator 的打包脚本，把文件夹压成 `.skill` 文件，方便分发：

```bash
python -m scripts.package_skill ./commit-message-writer
```

**装之前先看一眼。** 官方特意提醒过：Skill 里既能放指令也能放代码，恶意的 Skill 可能带来漏洞，或者偷偷把数据传出去。**只装信得过的来源**，装之前把里面的文件读一遍，重点看代码依赖、脚本素材，以及有没有偷偷连外部网络地址的指令。

## 说到底

回顾一下从零做一个 Skill 的主线：

1. **想清楚**——它做什么、何时触发、输出什么样、要不要测；
2. **写 `SKILL.md`**——`name` 合规、`description` 写黏人、正文讲原因给例子、控制 500 行内；
3. **拆资源**——详细文档丢 `references/`、确定性工作写成 `scripts/`、模板素材放 `assets/`；
4. **测两遍**——带 Skill vs 不带，写断言、汇总 benchmark、看反馈再迭代；
5. **调触发**——20 个查询专门优化 description，用留着的那部分考它，别让它死记硬背；
6. **校验打包**——validate 一遍，打包成 `.skill`，分发前让它通过审计。

一句话心法：**把 Skill 当成写给一个聪明但不了解你团队的新同事的岗位手册**——讲清为什么、给足例子、别啰嗦。剩下的，交给渐进式披露和测试循环。
